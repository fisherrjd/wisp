wisp 0.17.0 · wire 1

One work item, one tmux session.

wisp turns a unit of work into a running workspace: it finds the item, reprovisions the git worktrees it needs, writes a context file for the agent, and drops you into a tmux session named after it. Nothing it does destroys work.

And it has no concept of a supported agent. The command in the session is a command line you write, so there is no adapter layer and no list yours has to be on.

The model

Five nouns, and everything else follows from them.

System

A machine. This one, or one you reach over ssh. It owns its workspaces and answers for them; nothing here keeps a copy of what it holds.

Workspace

The container. Every repo checkout, docs/, .worktrees/ and the vault sit side by side inside it. Agents start here, so one cwd sees all of them.

Item

A folder in the vault. Its stable identity is only <repo>/<iid>, because slugs drift between what you typed and what GitLab derives from the title.

Worktree

A cache, deliberately. Branches are the real state. Delete a worktree and reopening the item reprovisions it.

Session

A tmux session tagged @wisp_item. The agent window at the workspace root, one shell per worktree for builds and dev servers.

Killing a session leaves worktrees and branches. Deleting a worktree leaves the branch. Closing an item out leaves every file it holds. There is no command that removes your work.

Three levels

Systems hold workspaces hold sessions, and wisp moves between all three.

LevelMove withWhy it is its own level
session next / prev, or the list Never leaves the workspace, so what is running elsewhere cannot get in the way of flipping between the work in front of you.
workspace ctrl-w for the tree, hop for the blind step Its own vault, its own GitLab group, its own sessions. Two workspaces holding the same slug get two sessions, not one.
system ← → in that tree A whole machine at a time, because up and down would otherwise mean several presses to get past one.

Hopping into a workspace lands on the session you were last in there, not on its picker, so a trip out and back is a round trip rather than a reset.

Items and state

An item is a folder in the vault, exactly two levels deep: <repo>/<iid>-<slug> for work with a ticket, _adhoc/<name> for work without.

The state ladder

+ gitlab — on GitLab, nothing local ○ folder — a vault folder, no session ● live — a session is running ? needs input — the agent is waiting on you ✓ done — closed out

The first four are a ladder. When the same item is found by more than one source the highest wins, so a live session always beats the vault folder it came from and the folder beats the GitLab row.

Done is not a fifth rung. The states are a ladder and merging keeps the highest, so a done item found again as a live session would have the flag overwritten by whichever source spoke last. Done is a separate axis: it says what you decided, not what the machine observed.

Why identity is the number, not the name

A local folder is named by hand; a GitLab row is named from the title, cut to four words. The same ticket routinely exists under two spellings. Deduplicating on <repo>/<iid> is what makes it one row — keeping your name and the highest state either source reported.

The picker

Type to filter, enter to open. The filter is fuzzy and matches the item name, not its GitLab title.

KeyDoes
enteropen the highlighted item
↑ ctrl-k / ↓ ctrl-jmove the cursor
ctrl-ncreate an item: a name, or a pasted GitLab link
ctrl-dclose the highlighted item out, asking what happened
ctrl-tshow the closed-out ones again
ctrl-xkill the highlighted item's session
ctrl-wopen the machine and workspace tree
ctrl-rdrop the GitLab cache and re-query
ctrl-uclear the filter
escquit, leaving everything running
ctrl-d and ctrl-x are two different kinds of finished. ctrl-x stops what is running and leaves the item. ctrl-d ends the work and leaves the list, writing done: true into the item's notes.md frontmatter. An item with a live session keeps its row either way: something is still on the machine, and hiding it would leave an agent with nothing pointing at it.

Closing out asks what happened

A closed-out item is one you stop seeing, so its note is the only thing left of it. On an item nobody has written anything about yet, ctrl-d opens a line:

ctrl-d 
 closing out  it was a caching bug in the router▏      one line on ledger-service/318
──────────────────────────────────────────────────────────────────────
enter close it out   ctrl-d close it bare   esc cancel

enter writes the line under a dated heading and sets the flag in one pass. ctrl-d again closes it bare, for work there is nothing to say about.

The ask exists because the two halves had come apart. Setting the flag was one keystroke and writing the summary was a trip to an editor, so the items that got closed out and the items that got written up were disjoint sets: every item carrying the flag had a note holding nothing but the flag. An item you have already taken notes on closes with no ceremony — the friction sits exactly where the record would otherwise be lost, and nowhere else.

Plain letters, not chords: nothing in the tree types, and wisp lives inside tmux, so whichever chord you use as your prefix would never arrive. ctrl-a is a common one and reaches nothing.

⚠ unreachable — fix ssh ✗ missing — fix by making a directory

Separate glyphs on purpose. Both are unusable, but a single mark for both would send you after the wrong one.

Commands

One global flag, -w, and it has to come first. Errors go to stderr and exit 1; everything else exits 0.

Sessions

What happens between pressing enter and having somewhere to work.

If a session already exists, wisp attaches and does nothing else. The layout below happens once, on first open — and the lookup is by identity, not by name, so a session started by an older wisp is reattached rather than duplicated.

WindowcwdRuns
agentthe workspace rootyour program:, with the context inlined
one per repothat repo's worktreea plain shell, for builds and dev servers
provisionthe workspace rootwisp provision, then closes itself

The agent sits at the workspace root because one cwd there sees the vault, docs/, every repo and every worktree. That is the whole point of the container model.

Provisioning never blocks opening. The script pre-warms a nix environment through direnv, and a cold evaluation takes long enough that waiting for it felt like the tool had hung. So the session opens straight away and missing worktrees are built in their own window — visible and interruptible rather than hidden behind a frozen picker.

The provisioning contract

wisp never runs git worktree add itself. It shells out to a script in your workspace, with a fixed argument list:

provision-worktree.sh <repo-path> <slug> <branch> --attach [--base <base>] [--no-install]

--attach is always passed: an item reopened after cleanup has a live branch but no checkout, and without it every reconstitution fails on "branch already exists".

The manifest

An item can span several repos. YAML frontmatter in orchestration.md says so, and records intent rather than paths — a path would be a cache pretending to be state.

---
repos:
  - repo: payments-api
    branch: feature/1042-retry-backoff
    base: main
  - repo: webhooks-worker
    branch: feature/1042-retry-backoff
---

Configuration

<workspace>/.wisp.yaml wins over ~/.config/wisp/config.yaml, and the environment wins over both.

The workspace file wins on purpose: the workspace is the unit that owns a vault, a set of repos and a GitLab group, so its config should travel with it rather than living in one global file that a second workspace would have to fight.

# <workspace>/.wisp.yaml
program: claude                 # runs in the agent window
install: false                  # install deps when provisioning
vault: working_items            # where items live
worktrees: .worktrees           # the worktree cache
provision: .claude/scripts/provision-worktree.sh
gitlab:
  group: your-group/subgroup
  username: you
  repo_pattern: '/subgroup/([^/]+)/-/'
  cache_ttl_min: 15

program: is the whole of wisp's agent support

program: is handed to tmux as a shell command line with the context file appended as one shell-quoted argument. Flags, environment prefixes and wrapper scripts are all already expressible in it, which is why there is no adapter layer here and no list of agents yours has to be on.

program: claude
program: codex
program: aider --model sonnet
program: .claude/scripts/agent-wrapper.sh

The one contract is that the prompt arrives as an argument. An agent that reads its prompt from stdin instead needs a wrapper script that does the reading: the cost of having no adapters, and a file you write once. WISP_PROGRAM overrides it for a single session, so trying a different agent on one item touches neither config file.

The user config, and only the user config, owns workspaces:, hosts: and default:. A workspace naming its neighbours would let one of them rename or hide another — and .wisp.yaml is a file you check in and hand to other people.

Workspace resolution, in order

1-w <name>An explicit answer skips the search entirely.
2WISP_WORKSPACEA path, when set.
3the nearest ancestorHolding a .wisp.yaml or a vault. The git approach — it is what lets wisp work from inside a repo or a worktree.
4the default workspaceFor running wisp from anywhere at all.
5the current directoryOnly so the error names somewhere you recognise.

repo_pattern

Matched against the whole work-item URL, with exactly one capturing group, which must be the repo directory as it is spelled in your workspace. GitLab nests projects arbitrarily, so there is no generic form for this and no sensible default. Anchoring on the literal /-/ is what stops the group segment being captured.

Remote workspaces

A workspace on another machine, in the same ring as the ones on this one.

The picker always runs locally. Only the agent session runs remotely. Running the picker on the far side over ssh -t would make every keystroke a network round trip for the sake of redrawing a list.

You register a machine, not a path. The machine already knows what it holds, so listing its workspaces here as well would be a second copy of a list only one side owns, and the two would drift the moment you made one over there.

wisp host add jade@eldo                  # the machine, and everything on it
wisp host add box jade@eldo              # calling it something else
wisp ws new scratch bigbox:~/scratch     # one workspace it has not registered
wisp ws new scratch -p bigbox:~/scratch  # and make it there too

Opening a remote item makes an ordinary wisp session here whose one window is an ssh -t into the machine that owns the work. That single decision is why next, prev, the ring, the last-visited session and the needs-input check all keep working on it unchanged.

What the far side needs

RequirementIf it is missing
wisp on PATH non-interactively wisp is not on PATH on eldo. The common one: ssh host cmd runs a non-login shell, so .bash_profile is skipped.
key-based auth cannot reach eldo: Permission denied. Background calls set BatchMode, so there is nowhere to type a password.
a wisp new enough wisp on eldo is too old for this (this one is 0.16.0)
the same wire number eldo runs wisp 0.14.0 speaking wire 0; this one speaks wire 1
a vault that exists Not an error: the row shows no vault at <path> on eldo.

The raw failure is exit status 255, which is true and useless. Six cases get their own message instead. A machine that will not answer keeps its own row, marked ⚠, rather than silently taking its workspaces out of the list.
